# String pages — architecture (not yet implemented)

Product feedback for this phase asked for dedicated per-string pages (e.g.
`/strings/yonex-bg80`) to support future SEO, sharing, and direct
recommendation/comparison entry points. Per that same feedback ("if full
implementation is too large, prepare the architecture instead of building
fragile shortcuts"), this phase does **not** ship string pages — the
current hash-routed single-page app (`src/App.tsx`'s `View` type) has no
per-resource routing at all, and bolting one route on without the rest
would be exactly the fragile shortcut the brief says to avoid. This
document is the plan for building it properly in a later phase.

## Why this needs real routing, not another hash view

Existing routes (`#finder`, `#compare`, `#impressum`, ...) are hash
fragments — never sent to the server, never distinctly indexable (see
`public/robots.txt` and `public/sitemap.xml`, which both explain the same
limitation). A `/strings/yonex-bg80` URL that's actually crawlable,
shareable, and bookmarkable needs a real path segment GitHub Pages can
serve — which means either:

1. **Static pre-rendering**: generate one static HTML file per string at
   build time (e.g. a small script that iterates `src/data/strings.ts`
   and writes `dist/strings/<slug>/index.html`), each with its own
   title/description/OG tags and a link back into the SPA. Works cleanly
   with GitHub Pages' static hosting and the existing `base: '/smash_lab/'`
   path config in `vite.config.ts`.
2. **Client-side routing with a real router** (e.g. adding a lightweight
   router and a GitHub Pages 404-redirect trick to support deep links).
   More invasive — touches the whole app shell — and was explicitly ruled
   out of scope for this phase ("no full Astro/Next.js migration").

Option 1 is the better fit for this project's existing static-site
architecture and should be the starting point when this is built.

## Proposed shape

- **Slug**: derived deterministically from `brand` + `name` (e.g. `yonex
  bg80` → `yonex-bg80`), computed by a small pure function — never a
  manually-maintained per-string field, matching this codebase's existing
  "never hardcode per-item data that can be derived" convention (see
  `src/logic/stringMapPosition.ts`'s own framing of the same principle).
- **Content**: the same data already rendered by `StringCard.tsx` and the
  comparison table (manufacturer ratings, specialist profile, retailer
  listings, price-per-metre) — no new data model needed.
- **Entry points once built**: a "View full details" link from
  `StringCard.tsx`, from each `RecommendationPodium.tsx` card, and from
  `StringMap.tsx`'s point labels — all three already have the exact
  `StringItem` needed, so wiring the link is a small, additive change.
- **Sitemap/robots**: once real paths exist, `public/sitemap.xml` gets one
  `<url>` entry per string (generated by the same build step, not
  hand-maintained) and `public/robots.txt` continues to `Allow: /`.

## What this phase changed to prepare for it (without building it)

Nothing yet — this document exists so the shape above doesn't need to be
re-derived from scratch later, and so no interim shortcut (e.g. faking a
route with more hash-view sprawl) gets built in its place.
